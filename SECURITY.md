# Security policy

## Reporting a vulnerability

To report a security vulnerability in Revex, **do not open a public
GitHub issue**. Email the maintainers directly
(`security@sachncs.dev` or the address listed in `package.json`)
with a description of the issue, reproduction steps, and the
impact you observed.

We will acknowledge receipt within 48 hours and provide a
timeline for resolution. Critical issues are handled before
non-critical issues; public disclosure is coordinated with the
reporter and lands alongside the fix.

## Supported versions

Security patches ship on the latest tag on the `master` branch.
Older tags receive best-effort fixes only.

| Branch | Status |
|---|---|
| `master` | Supported — current release line |
| Older tags | Best effort |

## Production hardening checklist

The following items are required for a production deployment. The
Revex CLI prints the same list at `revex docs hardening`.

### Secrets

- `REVEX_JWT_SECRET` is set, unique per deployment, and at least
  **32 characters**. Generate it with
  `openssl rand -base64 48`.
- `REVEX_TENANT_SECRETS_KEY` is set (32 bytes, hex) and **never**
  committed to source control.
- LLM provider API keys live only in `workspace_settings`, sealed
  by the workspace passphrase via AES-256-GCM. They never appear
  in plaintext on the wire or in logs.

### HTTP surface

- `REVEX_CORS_ORIGINS` is the real frontend origin
  (e.g. `https://app.example.com`). The default `localhost` origins
  are not safe for production.
- `REVEX_PROFILE=production` enables `Strict-Transport-Security`
  (`max-age=63072000; includeSubDomains; preload`) and rejects
  `allowOrigins: ['*']` at boot.
- `REVEX_CSP` provides a `Content-Security-Policy` header set
  appropriate for the app shell. A reasonable default is
  `default-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'`.
- `REVEX_TRUSTED_PROXY_CIDRS` is set when the API is behind a
  reverse proxy; without it the rate limiter ignores
  `X-Forwarded-For` and uses the socket peer address.

### Cookies and CSRF

- `revex_session` and `revex_workspace_key` are set with
  `HttpOnly; Secure; SameSite=Lax`. Both cookies must come from
  the API's `Set-Cookie` response, never from `document.cookie`.
- State-changing routes (`POST` / `PATCH` / `PUT` / `DELETE`)
  reject mismatched `Origin` headers with `403`. The web app
  forwards the browser `Origin`; server-to-server callers can
  pass `Origin` explicitly.

### Authentication

- JWTs are HS256 by default; set `REVEX_JWT_ALGORITHM=HS256` or
  `HS512` explicitly. Never use `none`.
- The workspace passphrase must be at least 8 characters; the
  JWT secret must be at least 32 characters
  (`JwtService` throws `ConfigurationError` if either is below
  floor).
- A non-default passphrase is required for every workspace;
  `REVEX_ALLOW_DEV_PASSPHRASE=1` is **forbidden** in production.

### Rate limiting and abuse

- `REVEX_RATE_LIMIT_PER_IP` defaults to 60 req/min/IP; raise or
  lower for your traffic.
- `REVEX_RATE_LIMIT_PER_WORKSPACE` defaults to 600 req/min; the
  middleware verifies the JWT signature before applying the
  per-workspace bucket — unauthenticated requests cannot rotate
  fake `workspace_id` claims to bypass the per-IP limit.

### Random identifiers

- All workspace, user, job, group, webhook, and feedback IDs are
  generated by `@revex/core`'s `newId(prefix)` helper, which uses
  `crypto.randomUUID()` (128 bits of entropy). Never use
  `Math.random()` for security-relevant identifiers.

### Telemetry and audit

- `REVEX_TELEMETRY_PROVIDER=langfuse` or `otel` for production.
  `noop` discards everything.
- The audit log table (`audit_event`) is append-only; rotate a
  backup before any destructive maintenance.
- The signed GitHub Actions workflows publish to npm via
  **Trusted Publishing (OIDC)**. There is no long-lived npm token
  in CI.

### Supply chain

- CI installs third-party tooling from pinned, checksummed
  artifacts only. No `curl ... | sh` in any workflow.
- `pnpm install --frozen-lockfile` is the install entry point;
  drift between `pnpm-lock.yaml` and `package.json` is a build
  failure.

## CI gates

Every push and pull request to `master` runs:

1. `pnpm install --frozen-lockfile`
2. `pnpm turbo run lint`
3. `pnpm turbo run typecheck`
4. `pnpm turbo run test`
5. `pnpm turbo run build`

A failed gate blocks the merge. Releases additionally run the
`release.yml` workflow on tag push and publish to npm via OIDC.

## Disclosure

We follow a coordinated disclosure model. We aim to ship a fix
within 14 days for critical issues and 60 days for non-critical
issues, with public disclosure once a fix is available.
